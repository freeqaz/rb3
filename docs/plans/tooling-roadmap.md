# RB3 Tooling Roadmap — Post-Tier-1 Sync

Plan for the next round of RB3 decomp tooling work, picking up where the
2026-05-11 Tier 1 sync (`docs/SYNC_WITH_DC3.md`) left off. Revised
2026-05-12 after a staff-engineer design review surfaced ground-truth
issues with the original plan: a stale match% baseline, an under-scoped
BSF estimate, a broken Step 1.1 verification command, an incorrect
pyelftools install claim, and an MCP-tool scoring formula that depended
on schema columns that don't exist.

Last updated: 2026-05-12.

## Prioritization principle

Rank by **impact-per-hour on the AI agent decomp loop**:

1. Does it unblock something agents currently get stuck on? (Highest priority.)
2. Does it tighten the edit → build → diff → decide cycle?
3. Does it raise the ceiling on match% (fewer AT_LIMIT calls)?
4. Does it make tooling self-maintaining (less manual bookkeeping)?

Native port work and shared-toolkit extraction are explicitly deferred — see
"Out of scope" at the bottom.

## Phase 1 — Implement Tier 2 vtable skills (~1 day)

**Why first:** plans are written (`docs/plans/vtable-skill.md`,
`docs/plans/resolve-vcall-skill.md`), the empirical findings are fresh, and
the shipped tooling immediately resolves a class of objdiff mismatches that
agents currently can't debug without manual disassembly reading.

### Step 1.1 — Verify the "one `__vt__N<class>` symbol per class" invariant — DONE 2026-05-12

The original command in this doc was broken in two ways: zsh's `**` is not
recursive without `setopt globstar`, and `awk`'s `FILENAME` is `-` when
reading from a pipe, so per-file context was lost (uniqueness was being
counted across nothing). Corrected:

```bash
setopt globstar  # zsh; bash users: shopt -s globstar
for f in build/SZBE69_B8/obj/**/*.o; do
    nm -g "$f" 2>/dev/null | awk -v file="$f" '/__vt__/ {print file, $3}'
done | sort -k2 | uniq -c -f1 | awk '$1 > 1' | head
```

**Result:** No class has more than one `__vt__N<class>` symbol across the
whole build. Top vtable-density files are Game.o (19), NetSync.o (17),
VocalTrackDir.o (14), GemTrackDir.o (14). The single-symbol invariant
holds. The multi-symbol fallback documented in `docs/plans/vtable-skill.md`
§ 4 stays a future-proofing note, not initial scope. See Step 1.7.

## Phase 2 — Quick agent-loop wins (parallelizable, ~2 days total)

**Why second (was Phase 3 in v1):** these items are independently
shippable, each pays for itself in days, and Step 2.1 (`next_target`)
feeds the validation-set selection for the more speculative Phase 3
spike. Doing Phase 2 first means Phase 3's go/no-go is made on better data.

### Step 2.1 — `mcp__orchestrator__next_target` MCP tool

Add to `scripts/orchestrator/mcp_server.py`. Queries `decomp.db` for
workable functions ranked by closeness to 100% and prior attempt count.
Filters out `verdict IN ('COMPLETE', 'AT_LIMIT')`. Inputs: optional unit
glob, optional `min_percent` floor. Returns top N with metadata (current
%, last attempt timestamp, last attempt outcome).

The original scoring formula needed a column the schema doesn't have, so
this is split into two sub-steps:

#### Step 2.1a — MVP scoring (~3 hr)

Use:

```
score = closeness_to_100 / (attempt_count + 1)
```

Both columns already exist on `functions` (verified 2026-05-12;
`attempt_count` is incremented in `scripts/orchestrator/database.py:582`
on every `record_attempt`). No schema changes; no new infra. Ships
immediately.

**Success criterion:** an agent in a fresh session can ask "give me 5 RB3
functions to work on right now" and get a list ranked by ROI without any
preamble.

#### Step 2.1b — Call-graph weighting (deferred, ~6 hr when picked up)

Original formula was `score = closeness_to_100 × log(fan_in + 1) / (attempts + 1)`.
`decomp.db` has no `fan_in` column and no call-graph table. Adding it
requires a static-analysis pass against the ELF or `.o` files (or a
Ghidra cross-ref dump), back-fill for ~41K functions, plus an incremental
refresh hook so it doesn't decay against new builds.

Schedule independently after 2.1a's rankings prove insufficient. Concrete
trigger: 2.1b becomes worth the work only if 2.1a's top-10 picks regularly
come back as low-impact (e.g. tiny leaf functions agents complete easily
but that don't unblock anything).

### Step 2.2 — Hook `batch_check` to the `report.json` build edge (~1-2 hr)

The original doc proposed two options (phony target, post-build hook in
`configure.py`) and recommended Option A. Both fail the stated success
criterion ("after a header change, decomp.db reflects the new 100%
matches with no manual intervention") because both require user
discipline.

**Option C — recommended:** chain `batch_check` to the existing
`build/SZBE69_B8/report.json` build edge as a follow-up rule, so plain
`ninja` always finishes by sweeping. `batch_check` reads `report.json`
(no per-function objdiff invocations — see
`.claude/skills/batch-check/SKILL.md`) and should run sub-second; the
"could slow the build" concern from Option B doesn't apply.

**Process:** measure the actual sweep cost on the existing report before
committing to Option C. If steady-state cost is >2s, fall back to
Option A (phony target) and document the manual step explicitly.

**Success criterion:** running plain `ninja` after a header change
leaves `decomp.db` reflecting the new 100% matches with no extra commands.

### Step 2.3 — `lookup_dc3` ranking by DC3 match% (~1-2 hr)

Current `lookup_dc3` (`scripts/orchestrator/mcp_server.py:1028-1084`) is a
simple grep — no ranking, no filtering, returns the first 20 of up to 1948
hits for common names like `Poll` (1948 confirmed empirically 2026-05-12).
Improve by:

1. Load DC3's `build/373307D9/report.json` (cache on path mtime). Confirmed
   present at `/home/free/code/milohax/dc3-decomp/build/373307D9/report.json`
   (14.9 MB, mtime 2026-05-11).
2. For each grep hit, find which DC3 unit it's in and look up the unit's
   match%.
3. Sort results by descending unit match% (higher = more reliable
   reference).
4. Add `--min-match` flag to filter to e.g. ≥90% units only.

**Success criterion:** `lookup_dc3 Poll --min-match 90` returns ≤20 hits,
all from DC3 units that decomp'd cleanly.

### Step 2.4 — `bin/sweep-untouched` script (~1 hr if 2.1 is done first)

Promote the focused subset of `scripts/dc3_compare.py`'s "find untouched
work" surface to a thin CLI wrapper:

```
bin/sweep-untouched system/char/ --min-size 100 --max-attempts 0
```

Lists untouched (zero-decomp) functions in the unit glob, ranked by size
descending, with `--max-attempts N` to filter out things that already
failed N times. `attempt_count` is already filterable via existing
`database.py` infrastructure (verified 2026-05-12).

**Implementation constraint:** share the ranking library function with
Step 2.1 — both should read from the same scoring code so the MCP tool
and the CLI never disagree. If 2.1 ships first, this is mostly a CLI
shim over the same library; if it ships in isolation, factor the ranking
out cleanly so 2.1 can pick it up without rework.

`bin/` confirmed not to contain `sweep-untouched` today (current contents:
`analyze-function`, `decompile`, `objdiff-cli`, `orchestrate`).

## Phase 3 — BSF permuter spike (~1-2 days; outcome decides full port)

**Why downgraded from "implement" to "spike" vs v1:** v1 of this doc
budgeted 1-2 days to "port" BSF, asserting that RB3 has "basic source
permuter integration" and that BSF's tracing logic is "compiler-agnostic."
Verification on 2026-05-12 found:

1. **No RB3 permuter substrate.** `scripts/permuter/` does not exist in
   RB3. RB3 appears to invoke upstream `decomp-permuter` via the
   `/permute` skill (witnessed by `permuter_cache.db` and
   `.permuter_work_*.d` files in the working tree), but the framework
   that DC3's BSF plugs into (~50 files, ~24K LOC under
   `dc3-decomp/scripts/permuter/`) is absent here.
2. **BSF is heavily MSVC-coupled.**
   `dc3-decomp/tools/compiler_trace/bsf_trace.py` hardcodes MSVC `c2.dll`
   RVAs (e.g. `0x026780`, `0x027242`), requires MSVC `/FAs` assembly
   listings, and parses Xenon `__savegprlr_N` / `stmw r_N` prologues. The
   *concept* (declaration-order → register coloring) ports to MWCC; the
   *machinery* needs a from-scratch equivalent — and there is no obvious
   analogue to MSVC's c2.dll instrumentation point in MWCC.

A realistic full-port estimate is 1-2 weeks (stand up RB3 permuter
substrate, design and implement an MWCC register-introspection mechanism,
integrate targeted mutations, build and validate). Before committing to
that, do a spike to scope the unknowns.

### Step 3.1 — Read DC3's BSF design (~2-3 hr)

Source: `/home/free/code/milohax/dc3-decomp/docs/permuter/bsf-engine.md`
(177 lines, verified 2026-05-12) and the implementation under
`dc3-decomp/tools/compiler_trace/` (15 files including `bsf_trace.py`,
`asm_diff.py`) and `dc3-decomp/scripts/permuter/regmap_solver.py` (~850
LOC; the BSF integration point). Understand the color → GPR mapping, the
c2.dll instrumentation point, and how it integrates with the rest of the
permuter.

### Step 3.2 — Audit RB3's current permuter state (~2-3 hr)

Question to answer: how is `/permute` actually wired today? What invokes
upstream `decomp-permuter`? What writes `permuter_cache.db`? What are the
`.permuter_work_*.d` files? Once we know the substrate (or can confirm
its absence definitively), we know whether the full-port cost is "port
BSF on top of an existing permuter" or "stand up the whole permuter
substrate first."

### Step 3.3 — Write `docs/plans/bsf-permuter-port.md` (~1 day)

Cover:

- What DC3's BSF does (from 3.1) — mechanism, instrumentation point,
  output format, integration with the permuter.
- What RB3 has today (from 3.2) — substrate, gaps.
- **The MWCC introspection question (the genuinely unknown piece):** what
  mechanism on RB3 can give us per-variable register-color information?
  MWCC doesn't have a c2.dll. Options to investigate: parsing MWCC's
  listings output (`-S` / `.s` files), DWARF location-list inspection in
  the Bank 5 debug ELF, or a modified objdiff pass. Pick a candidate and
  justify it.
- **Concrete validation set: 5 specific functions in the 95-99% range,
  pre-selected and locked in this doc before any implementation.**
  599 candidates exist per `decomp.db` query as of 2026-05-12 (e.g.
  `main/App/__ct__3AppFiPPc` at 98.14%). Pick using the new `next_target`
  tool from Phase 2.
- **Strengthened success bar:** "≥3 of 5 hit 100% within N permutation
  iterations" (pick N), not "at least one hits 100%." Add an explicit
  kill criterion: "fewer than 1 of 5 implies BSF doesn't pay for itself;
  deprecate or escalate before further investment."
- Effort breakdown for the actual port (post-spike), in the same
  step-by-step shape as Phase 1 / Phase 2, so the next session can
  schedule it without re-deriving the cost.

The deliverable of Phase 3 is **this doc**, not a working BSF. The doc
gates the decision on whether to spend 1-2 weeks on the full port.

### Step 3.4 — Go/no-go review

After Step 3.3, decide:

- **Go:** schedule the full port as Phase 4 (separate roadmap pass).
- **No-go:** record the postmortem in the same doc; revisit when
  match%-improvement strategies on register-swap residuals come back into
  scope (e.g. after the tail-end push toward 90% via other levers).

Do not silently shelve. Either ship the implementation or ship a written
"why we didn't" — both have value; the in-between state of "we sort of
tried" wastes future agents' time re-deriving the same negative result.

## Sequencing rationale

```
Phase 1 (vtable / resolve-vcall)
    │
    ├──► unblocks vtable-offset diagnosis in objdiff
    │
    ▼
Phase 2 (quick wins, parallelizable)
    │
    ├──► next_target + ranked lookups + ambient batch_check
    │    tighten the agent loop on top of Phase 1's new visibility
    │
    ▼
Phase 3 (BSF spike → go/no-go)
    │
    ├──► validation set picked using next_target's ROI ranking
    └──► output is a written port plan + decision, not code yet
```

v1 of this doc placed BSF as Phase 2 on the strength of a "79% cross-
platform fuzzy match" claim that doesn't appear in any RB3 metric. The
actual gap from 73.6% fuzzy is real, but the cost-to-close via BSF is
large enough (weeks, not days) and uncertain enough (no MWCC equivalent
of MSVC's c2.dll instrumentation point) that committing to it before
scoping is premature. Reordering puts the cheap-and-certain wins first
and lets the BSF decision ride on the spike.

Phase 1 and Phase 2 each have explicit success criteria; Phase 3's
"success" is a written decision, with a kill criterion baked into the
deliverable (Step 3.3) so it can't quietly bog down without producing
either code or a postmortem.
