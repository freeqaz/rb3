# char-Load 5b — Lane: CharClip::Load ("version-desync")

Investigation date: 2026-06-11. Goal: unblock `BandHeadShaper::Init` (src/system/bandobj/BandHeadShaper.cpp:137 `_tmp0 = false;`) which hard-gates head-milo loading on HX_NATIVE because three char Load functions are claimed not byte-correct reading big-endian head.milo on the LE native host. This lane covers **CharClip::Load**.

## TL;DR (the finding the fix step needs)

**CharClip::Load's own read sequence is already byte-correct on the native LE host. It is NOT the source of a version-desync.** Every field it reads goes through `BinStream::operator>>` → `BinStream::ReadEndian`, which is already HX_NATIVE-gated correctly (BinStream.cpp:164-182, swaps when the file is big-endian on a LE host). The version word, all ints, bools, and strings read with correct width/endianness.

- objdiff: `Load__8CharClipFR9BinStream` = **98.3%** match. The remaining diffs are 100% stack-frame-shift (+0x10), REGISTER_SWAP (r3↔r4), and ADDRESS_RELOCATION_NOISE — pure at-limit/permuter-class noise, **no logic/read-order divergence**. The source faithfully encodes the target read sequence.
- Therefore **no source change is needed in CharClip.cpp for correctness**, and none should be made (any edit risks regressing the 98.3% Wii match for zero native benefit).

**The real desync lives in CharClip::Load's version-gated callees — the OTHER two lanes** (CharBonesSamples.cpp:457 and CharBones.cpp:1354). CharClip dispatches into them; when one of them mis-reads, the stream cursor desyncs and a later `ReadString` reads a garbage 4-byte length → `MILO_FAIL("String chars %d > %d")` (BinStream.cpp:45). The "version-desync attributed to CharClip" is really CharClip handing a correctly-positioned stream to CharBonesSamples, which then mis-reads.

## Ground-truth read sequence (verified against Bank-8 target asm)

Version word, read once at the top:
```
LOAD_REVS(bs):   int rev;  bs >> rev;            // 4-byte ReadEndian  (asm: li r5,0x4; ReadEndian)
                 gRev    = getHmxRev(rev) = rev & 0xffff   ;  // sth gRev   (low 16 bits)
                 gAltRev = getAltRev(rev) = (unsigned)rev >> 16 ; // sth gAltRev (high 16 bits)
ASSERT_REVS(0x13,0):  cmplwi gRev, 0x13          // gRev valid range: <= 0x13, gAltRev == 0
```
`getHmxRev`/`getAltRev`: src/system/obj/Object.h:495-497. `gRev`/`gAltRev` are `static unsigned short` of CharClip (ObjMacros.h:414-416). The packed int has the real version in the LOW 16 bits, alt-rev in the HIGH 16 bits — this is the endian-critical packing, and it reads correctly on native because `bs >> rev` is a single 4-byte ReadEndian (NOT two 2-byte reads).

Then `gOldRev` (a global `int`, CharClip.cpp:27):
```
if (gRev < 0x10) bs >> gOldRev;  else gOldRev = 0xD;   // 4-byte
MILO_ASSERT(gOldRev > 1, 0x523);
```
Body (all 4-byte ReadEndian or fixed-buffer ReadString, every one verified `li r5,0x4`/`0x80`/`0x100` in CharClip.s:4624-4920):
- `LOAD_SUPERCLASS(Hmx::Object)`
- if gRev<0x12: `bs >> x; bs >> y;` (two throwaway ints)
- `bs >> mFramesPerSec` (float); `bs >> mFlags` (int); `bs >> mPlayFlags` (int)
- if gOldRev<0xD: throwaway int
- if gOldRev>3: `bs >> mRange` (float)
- relative: gOldRev>5 → `mRelative.Load(bs,false,nullptr)` (ObjPtr::Load → `ReadString(buf,0x80)`); else gOldRev>4 → 1 bool; else null
- if gOldRev in {9,10}: 1 bool
- if gOldRev>9: `int oldVer; bs >> oldVer;` (4-byte), `MILO_ASSERT(oldVer<0x7fff)`, `mOldVer = oldVer` (sth to short@0x42) — **target reads 4 bytes then narrows; source matches (NOT a `short` 2-byte read)**
- if gOldRev>0xB: `bs >> mDoNotCompress` (bool, 1 byte)
- `mTransitions.Load(bs)` (CharClip.cpp:700; reads 4-byte counts + `ReadString(buf,0x100)`; **already has an HX_NATIVE LP64 alloc-size fix at CharClip.cpp:742-758**)

- **bones samples** (the dispatch into the other lanes):
  - if gRev>0xC: `mFull.Load(bs); mOne.Load(bs);` → CharBonesSamples::Load (CharBonesSamples.cpp:459, reads its OWN `gVer` via `bs>>gVer`)
  - else: `CharBonesSamples::SetVer(gRev); mFull.LoadHeader(bs); mOne.LoadHeader(bs);` (+ samps if gRev>7) `mFull.LoadData; mOne.LoadData`

For the RB3 head.milo the rev is high (>0x12: it reads mSyncAnim and a full mBeatTrack; >0xC: it takes `mFull.Load`/`mOne.Load` which re-read gVer), so the bones path that desyncs is **CharBonesSamples::Load** (lane 2), reached via `mFull.Load(bs)`.

## Why there is NO desync inside CharClip::Load itself

The endianness machinery is already native-correct:
- `BinStream::ReadEndian` (BinStream.cpp:164-182) under `#ifdef HX_NATIVE` swaps iff `!mLittleEndian` (i.e. iff the FILE is big-endian) — exactly right for a big-endian head.milo_xbox/_wii on an x86_64 LE host. This is the same precedent as the VorbisReader CTR-seek fix.
- The version word is a single 4-byte read (`bs >> rev`), not two 2-byte reads, so the LOW-16/HIGH-16 split in `getHmxRev`/`getAltRev` lands on the correct half after the 4-byte swap.
- `mOldVer`/`oldVer` is read as a full `int` (4 bytes) then narrowed to the `short` member — matches target asm; no 2-vs-4 byte mismatch.
- All strings go through `ReadString(buf, N)` / `operator>>(String&)` which read a 4-byte length then raw bytes — width-stable.
- No raw pointer or `sizeof`-derived field is read off the wire in CharClip::Load; ObjPtr/Symbol/vector LP64 size growth does not change the bytes consumed (names are length-prefixed strings).

## Concrete fix for THIS lane

**No code change to CharClip.cpp.** Two action items:

1. **Fix lanes 2 & 3 first** (CharBonesSamples::Load @ CharBonesSamples.cpp:457-463 + LoadHeader/LoadData/ReadCounts; CharBones::Bone operator>> @ CharBones.cpp:1352). Those are where the cursor actually desyncs; the garbage-length `ReadString` MILO_FAIL surfaces there. CharClip just routes the stream into them.
2. **Re-test CharClip after lanes 2&3 land.** Once CharBonesSamples/CharBones read correctly, CharClip::Load should consume head.milo's CharClip chunk end-to-end with no further change. If a residual desync remains, the only CharClip-side suspect is the `mTransitions.Load` LP64 alloc fix (CharClip.cpp:742-758) — already present, verify `temp + 8*numNodes` matches the actual LP64 NodeVector stride after lanes 2&3 are correct.

If, after lanes 2&3, a CharClip-specific native fix is ever required, it MUST be `#ifdef HX_NATIVE`-gated (precedent: CharClip.cpp:187-202 StartBeat/EndBeat empty-track guard, and CharClip.cpp:742-758 Transitions LP64 alloc) — never a match-neutral edit, because CharClip::Load is at 98.3% and any reorder regresses the Wii build.

## Gate recommendation for BandHeadShaper

The `_tmp0 = false;` gate (BandHeadShaper.cpp:137) can be lifted only after lanes 2 & 3 are byte-correct. CharClip::Load itself is not the blocker and needs no change to lift the gate.
