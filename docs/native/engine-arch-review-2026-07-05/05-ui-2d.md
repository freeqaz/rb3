# Lane 5 — UI / 2D Rendering Parity

**Reviewer:** Opus review agent (lane `ui-2d`)
**Date:** 2026-07-05
**Scope:** UI/text/2D render parity — why the song library page and HUD keep having layout bugs.
**Verdict:** **refactor** (structurally salvageable; the UI subsystem is faithful where it matters,
but the render backend re-derives state the engine already computes, and a family of "bugs" are
actually a *data-format* mismatch that no amount of render heuristics will cleanly fix).

---

## Executive summary

The single most important finding for this lane:

> **The UI layout code is FAITHFUL. The native build compiles the RB3 decomp's own
> `src/system/ui/*.cpp` (UIList, UILabel, UIScreen, UIPanel) and `src/system/rndobj/Text.cpp`
> (RndText layout/wrap/width) directly** (`rb3/native/CMakeLists.txt:250,261` glob
> `ENGINE_RNDOBJ`/`ENGINE_UI`). There is **no native reimplementation of text layout, wrapping,
> width measurement, or UIList slot math.** Those run the exact same code that produces the Wii
> binary. Therefore the song-library and HUD bugs are **NOT layout-computation divergences.**

Given that, the bugs decompose into three buckets, and only two of them are the engine's fault:

1. **DATA divergence (the dominant cause).** The native/web port forces
   `TheLoadMgr.mPlatform = kPlatformXBox` and loads **Xbox 360 `.milo_xbox` assets** from
   `orig-assets/extracted` (`rb3/native/src/main_native.cpp:360,527,715`), while the decomp code
   was written to match Wii-binary behavior on **Wii-authored data**. The 360 milos differ in ways
   the Wii-decomp code doesn't expect: non-square font atlases, widget *classes* (plain `UILabel`
   where Wii used `AppLabel`), and slots authored visible-not-hidden. This produces the
   squished/too-tall text, the stale-slot overlap, and the HUD score-not-updating — **all three
   canonical song-select/HUD bugs are data-format mismatches, not renderer bugs.**

2. **RENDER-backend divergence.** `Rnd_Wgpu_RB3.cpp` (7,017 lines) re-derives material and camera
   state from scratch instead of consuming what the faithful engine already computed. Text is
   detected by a name heuristic (`!mesh->Name()[0]`), font-atlas alpha is routed to RGB by a
   per-symptom flag, and the camera projection is rebuilt from `YFov`/window-aspect while the
   faithful `RndCam::mWorldProjectXfm` (which already honors `mScreenRect`, `mZRange`, aspect) is
   computed and then thrown away.

3. **TRANSFORM-propagation gap.** The hub highlight-bar and scrollbar-thumb "wrong position" bugs
   are a real engine defect: `SetWorldXfm` on a UI labelDir does not reach the skinned corner-bone
   parent chain, so skinned UI meshes render at the world origin. This is lane-3 territory but
   surfaces as UI breakage; the current fix is a name-scoped translation injection.

**The "fix pattern smell" the coordinator flagged is real and correctly diagnosed.** The
per-symptom heuristics (`UiRenderHeuristics.h`, the ~120-line inline text block in
`Rnd_Wgpu_RB3.cpp:5760-6100`, `RB3_NO_HUB_HIGHLIGHT_FIX`, `RB3_NO_HUB_BAR_PLACEMENT_FIX`,
`RB3_CROWD_DIM`, color-icon name exclusion) are papering over exactly two root causes: (a) a
data-format mismatch that wants an *asset-layer* fix, not a render fix; and (b) a backend that
doesn't consume faithful engine state.

## 1. Heuristics audit

### 1a. `src/platform/UiRenderHeuristics.h` — the whole file

```cpp
inline bool NativeShouldForceTextAlpha(bool isTextMesh, BaseMaterial::Blend blend, float alpha) {
    return isTextMesh && blend == BaseMaterial::kBlendSrcAlpha && alpha < 0.01f;
}
```

- **MEASURED:** This is the entire file. Its only referent is the test
  `tests/test_rndcam_projection.cpp:274-278` — **it is not called from any production code path**
  (grep across `milo-native-engine/` + `rb3/native/`). It is effectively dead. The real UI text
  logic lives inline in `Rnd_Wgpu_RB3.cpp`. So "audit every heuristic in `UiRenderHeuristics.h`"
  yields one dead predicate; the actual heuristic surface is the inline block below.

### 1b. Text-mesh detection — `Rnd_Wgpu_RB3.cpp:5772`, `Mesh_Wgpu.cpp:188`, `MeshGpuCache.cpp:226`

```cpp
bool isTextMeshHeur = mesh->Name() && mesh->Name()[0] == '\0';
```

- **Symptom patched:** RndText glyph submeshes are unnamed, so this discriminates "text" from
  scene geometry.
- **Faithful mechanism:** MEASURED — `RndText::UpdateMesh`/`CreateLines`
  (`rb3/src/system/rndobj/Text.cpp`) builds per-font submeshes via `Hmx::Object::New<RndMesh>()`
  and never assigns a name. On Wii, text is not distinguished by "no name" — it's distinguished by
  its **material**: text materials are authored with `pre_lit`/`use_environ` flags and a font
  texture whose glyphs live in the alpha channel, and `WiiMat::Select` outputs the register color
  directly (`GX_SRC_REG`, no lighting). The native code approximates "is this a text material" by
  "is the mesh nameless."
- **Replaceable?** Partially. The name test is a *proxy* for "has a font-atlas material." It is
  fragile precisely because 360 impostor-crowd billboards are *also* nameless with a nameless
  material (`Rnd_Wgpu_RB3.cpp:6054-6060` documents this collision), and NAMED score/scoreboard
  digit meshes are text but *not* nameless (`:5807-5865`, the `isLikelyUiText` broadening). The
  principled replacement is to key off the material's authored `pre_lit`/font-texture properties
  (which the decomp `RndMat` carries) rather than the mesh name. See §5.

### 1c. `useAlphaAsRGB` (font glyph alpha → luminance) — `Rnd_Wgpu_RB3.cpp:5946-5962`, `MaterialSetup.cpp:171`, shader `standard_wgsl.inc:755`

```cpp
bool isColorIconFont = matName[0] && std::strstr(matName, "icon") != nullptr;
mu.useAlphaAsRGB = (isTextMeshHeur && !isColorIconFont) ? 1.0f : 0.0f;
```

- **Symptom patched:** RB3 font atlases are DXT5 with the glyph shape in the **alpha** channel and
  RGB==0; the default diffuse path (`baseColor.rgb *= diffuseSample.rgb`) collapses text to black.
  `useAlphaAsRGB` switches the shader to `baseColor.rgb *= diffuseSample.a`. The `"icon"` name
  exclusion patches the *white-icon-blob* regression: instrument-icon fonts carry real RGB artwork
  with alpha as a circular cell mask, so alpha-as-RGB wrongly discards the art.
- **Faithful mechanism:** MEASURED — on Wii the font material's TEV stage is authored to take the
  texture's alpha as the color source for letter fonts, and RGB for icon fonts. This is *material
  data*, not a heuristic — the milo authors it per material. The native code re-derives it from the
  mesh-name + material-name substring instead of reading the material's authored TEV/color-source
  configuration.
- **Replaceable?** Yes in principle, but the faithful path requires modeling the Wii TEV
  color-source authoring (or the 360 equivalent). Short of that, the name heuristics are load-bearing.

### 1d. Prelit / unlit force for text and UI overlays — `Rnd_Wgpu_RB3.cpp:5922`, `:5934`

```cpp
mu.prelit = (mat->mPreLit || isTextMeshHeur || isUiHighlightOverlay) ? 1.0f : 0.0f;
mu.unlit  = (!mat->mUseEnviron && !mat->mPreLit) ? 1.0f : 0.0f;
```

- **Symptom patched:** unlit/prelit UI collapses to black when multiplied by the menu pass's
  near-zero lighting term.
- **Faithful mechanism:** MEASURED — `mu.unlit = (!mUseEnviron && !mPreLit)` is *correct and
  faithful*: it mirrors `WiiMat::Select`'s `GX_SRC_REG` path (register color, no ambient/lights/
  vertex color). This one is a genuine implementation of the Wii rule, not a symptom hack. The
  `|| isTextMeshHeur || isUiHighlightOverlay` additions are the heuristic layer on top.
- **Replaceable?** The `unlit` term is already the faithful mechanism — keep it. The
  `isTextMeshHeur`/`isUiHighlightOverlay` extras become unnecessary if text/overlay materials are
  correctly recognized as `pre_lit`/`use_environ=0` from data (which they are on Wii).

### 1e. Color floor for UI text — `Rnd_Wgpu_RB3.cpp:5910-5916`

```cpp
if (isLikelyUiText) { mu.color[0]=max(0.6f,...); mu.color[1]=...; mu.color[2]=...; }
```

- **Symptom patched:** font materials whose authored `GetColor()` is (0.2..0.5) read fine on a
  480i CRT but are invisible on a 720p canvas over near-black panels.
- **Faithful mechanism:** none — this is a **pure fudge with no faithful basis.** The comment itself
  admits the color is data-driven and "fine on a 480i CRT (retail target)." Lifting to ≥0.6 is a
  legibility hack, not parity. **Kill candidate** (it can only *diverge* from retail).

### 1f. Menu highlight-bar color/placement — `Rnd_Wgpu_RB3.cpp:5843-5865` + `4479-4510`, flags `RB3_NO_HUB_HIGHLIGHT_FIX`, `RB3_NO_HUB_BAR_PLACEMENT_FIX`

- **Symptom patched (color):** `highlight_main.mat` has `pre_lit=0, use_environ=1`, so `unlit` is
  false → it takes the LIT branch → menu near-zero lighting collapses the yellow bar to black.
  Name-scoped to `highlight_main`/`highlight_pattern` and routed through the prelit path.
- **Symptom patched (placement):** MEASURED, and this is a **real transform bug, not a data
  problem** — `Rnd_Wgpu_RB3.cpp:4459-4510`: the bar is a *skinned* UI mesh whose corner bones carry
  the quad; `UILabel::UpdateAndDrawHighlightMesh` sets the per-focus placement via
  `mLabelDir->SetWorldXfm(WorldXfm())` (`src/system/ui/UILabel.cpp:334`), but on native the corner
  bones' transform PARENT (`pentatonic_display`) stays at the origin — `SetWorldXfm` lands on the
  mesh/labelDir but not on the bones' parent chain — so the skinned palette places the bar at the
  world origin (screen center). The fix injects only the mesh WorldXfm *translation* into
  `obj.world` for the two named meshes.
- **Faithful mechanism:** the placement bug is the same root cause as the crowd/drum-kit placement
  bugs (lane 3): skinned meshes whose world placement comes via `SetWorldXfm` rather than baked
  bone world coords. Fixing the general propagation kills this heuristic *and* the scrollbar-thumb
  one below.
- **Replaceable?** Yes — fold into the lane-3 transform-propagation fix.

### 1g. Scrollbar-thumb placement — `Rnd_Wgpu_RB3.cpp:4512-4535`

- **MEASURED:** identical mechanism to 1f — `scrollbar.mesh` is a skinned UI mesh in a *shared*
  `scrollbar_display.milo` dir drawn after `pDir->SetWorldXfm(WorldXfm())`; the static sibling
  `scrollbar_bg.mesh` follows the fresh dir world but the thumb's bones don't re-inherit it, so the
  thumb stays at the origin. Same root cause, same kill target.

### 1h. Text z-mode force — `Rnd_Wgpu_RB3.cpp:6318`

```cpp
if (isTextMeshHeur) zMode = WgpuZMode::Disable;
```

- **Symptom patched:** HUD/menu text z-occluded by closer 3D panels.
- **Faithful mechanism:** MEASURED — the faithful engine handles UI-over-3D layering via
  `RndCam::mZRange` (`src/system/rndobj/Cam.h:117`, the "leave some z-buffer for HUD overlay
  objects" sub-range) plus draw order, **not** by disabling depth per text mesh. The native code
  ignores `mZRange` entirely (see §4) and substitutes a per-mesh depth-off heuristic.
- **Replaceable?** Yes, by honoring `mZRange` in the projection (§4/§5), which is the faithful
  layering mechanism and doesn't need a text discriminator at all.

### 1i. Crowd-dim / impostor-billboard — `Rnd_Wgpu_RB3.cpp:6036-6090`, flags `RB3_CROWD_DIM*`

- Not strictly UI text, but it *reuses the text heuristic*: the impostor crowd billboards are
  nameless with a nameless material, so `isTextMeshHeur` mis-tags them; the code has to re-exclude
  them (`worldCam && !skinned && isTextMeshHeur && matName[0]=='\0'`). This is direct evidence the
  nameless-mesh proxy for "text" is unsound — it collides with a whole non-text draw family.

**Heuristic count:** ~8 distinct UI special-cases, ~6 `RB3_*` opt-out flags, spread across a
120-line inline block plus a placement block 1,300 lines earlier — none in `UiRenderHeuristics.h`.

## 3. The DATA question — 360-ARK assets on a Wii-decomp engine

**MEASURED, and this is the crux of the lane.** The port loads Xbox 360 assets
(`TheLoadMgr.mPlatform = kPlatformXBox`, `main_native.cpp:360/527/715`, `.milo_xbox` extension,
`orig-assets/extracted`) but runs the Wii-decomp UI/render code. The retail-screenshots README
(`images/retail-screenshots/README.md`) says the *layout* is identical across Wii/360/PS3 (same
Milo scenes) — and it is, at the scene-graph level — but the *asset encoding* is not:

1. **Font atlases are non-square on 360** (higher-res: 512×1024, 512×256) vs square on Wii
   (512×512). `RndFont::Load` bakes `mCellSize = trueCell * atlasDim`, so the byte-matched
   `mCellSize.y/mCellSize.x` aspect is only correct for a square atlas. → squished/too-tall text.
   The native `CellDiff()` override (`Font.h:97-124`) recovers the platform-independent aspect from
   the normalized UV cell — this is actually a **principled** fix, not a fudge.
2. **Widget classes differ.** 360 milos author list slots and `score.lbl` as plain `UILabel`;
   Wii-decomp code `dynamic_cast<AppLabel*>` them and either asserts or drops the text
   (`MusicLibrary.cpp:1117-1118`, `UILabel.cpp:952`).
3. **Slot visibility differs.** 360 draws slots the Wii authored hidden → the
   `MusicLibrary::Text`-override-doesn't-clear contract violation surfaces as overlap.

**Principled handling (ranked):**

- **Best: run Wii assets.** The target binary is Wii; the decomp matches Wii data exactly. If the
  port extracted and loaded the Wii `.milo` set, *every* item above disappears with zero
  heuristics. The reason 360 is used is asset availability/resolution — a product decision, not a
  technical necessity. This should be re-evaluated as the highest-leverage UI-parity lever.
- **Second: a data-normalization/asset-translation layer.** If 360 assets must be used, translate
  them at load into the shape the Wii-decomp code expects (square-normalize font cell metrics,
  promote `UILabel`→`AppLabel` where the code casts, mark author-hidden slots). This centralizes
  the mismatch in one place instead of scattering `#ifdef HX_NATIVE` fixups across UI + band3.
- **Worst (current): per-symptom `#ifdef HX_NATIVE` patches** in the faithful source and render
  heuristics. This is what produces the "one fix per screen" churn.

The `CellDiff()` override is the *good* version of handling #1 (data-derived, scoped to non-square
atlases, Wii path untouched). The `MusicLibrary::Text` clear and `set_score_or_stars` handler are
the *acceptable* versions of #2/#3 but they pollute the faithful source. All three want to move
into an asset/data layer.

## 4. The 2D draw path — camera / z / blend, native vs faithful

### Camera projection

**MEASURED — the native backend re-derives the projection and discards the faithful matrix.**
`WriteSceneUniforms` (`Rnd_Wgpu_RB3.cpp:1308-1400`) calls `cam->UpdateLocal()` — which computes the
faithful `mLocalProjectXfm`/`mWorldProjectXfm` (`src/system/rndobj/Cam.cpp:155-192`) — and then
**ignores those** and builds its own perspective matrix from `YFov`, near/far, and
`window W/H` (`:1362-1392`).

The faithful projection is:
```
ratio = (mScreenRect.h / mScreenRect.w) * mUnknownFloat * TheRnd->YRatio()   // Cam.cpp:156
x-scale = ratio / tan(yfov/2),  y-scale = -1 / tan(yfov/2)                    // Cam.cpp:175-176
```
The native projection is:
```
aspect = windowW / windowH
sx = 1/(tan(yfov/2) * aspect),  sy = 1/tan(yfov/2)                            // Rnd_Wgpu_RB3.cpp:1383-1387
```

- `TheRnd->YRatio()` for `kWidescreen` = **0.5625** (= 9/16) (`Rnd.cpp:235-237`), and the default
  aspect is `kWidescreen` (`Rnd.cpp:217`). For a full-screen cam (`mScreenRect`=(0,0,1,1),
  `mUnknownFloat`=1) on a 16:9 window, faithful `x-scale = 0.5625/tan` and native `sx = 0.5625/tan`
  — they **coincidentally match.** This is why UI mostly lands and the bugs are "near-parity" rather
  than wholesale-wrong.
- **What native silently drops:** `mScreenRect` (viewport sub-rect + its aspect term),
  `mUnknownFloat` (SetFrustum's 4th param), the engine's own `GetAspect()`/`YRatio()` adaptation,
  and `mZRange` (the Z-buffer sub-range used for HUD-over-3D layering). Any cam that authors a
  non-default `mScreenRect`/`mUnknownFloat`, or a non-16:9 window, will diverge. This is a latent
  bug generator, and it's why depth layering needs the per-mesh `zMode=Disable` heuristic (§1h)
  instead of the faithful `mZRange`.

### Blend & z

- **MEASURED:** blend/zmode are taken directly from `RndMat` (`:6306-6312`), with the enum values
  documented as 1:1 with the Wii `RndMat::Blend`/`ZMode` constants — this is faithful.
- **Alpha-write masking** (`:6343-6352`): native masks framebuffer alpha writes for non-RT passes
  because RB3 UI fill quads have `color.alpha=0` under Src blend, which would propagate α=0 to the
  framebuffer and make the PNG readback transparent. This is a native-output concern (readback), not
  a Wii-parity concern, but it's benign.

### Draw ordering — is `TransparentQueue` equivalent to Wii order?

**MEASURED — `TransparentQueue.cpp`/`FlushTextDraws`/`FlushTransparentDraws` are NOT used by the RB3
backend.** They belong to DC3's `Mesh_Wgpu.cpp` path (grep: zero references to
`QueueTransparentDraw`/`FlushTextDraws`/`DrawMeshImmediate` in `Rnd_Wgpu_RB3.cpp`).
`BandRnd::DrawMesh` (`:3837`) issues `mPass.DrawIndexed(...)` **immediately** (`:6383`) in submission
order. So for RB3:

- UI/2D draw order = the faithful scene-graph traversal / `DrawShowing` order = **Wii painter order.
  Equivalent.** There is no back-to-front re-sort that could reorder UI elements.
- The DC3 `sTransparentQueue` back-to-front `distSq` sort (`TransparentQueue.cpp:129`) — which
  *would* be wrong for co-planar 2D UI — is simply not in the RB3 path. Good.
- Caveat: because RB3 draws everything (3D + UI) in one pass with per-mesh zMode, correct UI-over-3D
  compositing depends on (a) text `zMode=Disable` (the heuristic) and (b) UI being submitted after
  3D. Both hold today, but they're the render-side substitute for the faithful `mZRange` layering.

## 5. Recommendations — path to UI parity

### A. Kill list for heuristics (in dependency order)

1. **Re-evaluate loading Wii assets instead of 360 `.milo_xbox`.** This is the highest-leverage
   single change: it deletes the entire DATA bucket (squished text, stale-slot overlap, widget-class
   mismatch) at the source. If asset availability blocks this, build a **load-time
   asset-normalization layer** (§3, option 2) that: square-normalizes font cell metrics, promotes
   the specific widgets the code `dynamic_cast`s, and honors author-hidden slots — one file instead
   of scattered `#ifdef HX_NATIVE`.
2. **Consume `RndCam::mWorldProjectXfm` instead of rebuilding the projection.** The faithful engine
   already computes the world→clip transform honoring `mScreenRect`, `mUnknownFloat`, aspect. Adapt
   it to WebGPU NDC once (z-range + handedness), and delete the ad-hoc `YFov`/window-aspect matrix.
   This automatically fixes any non-16:9 window and any cam with a custom viewport, and — critically
   — makes `mZRange` available, which lets you **delete the `zMode=Disable` text heuristic** (§1h).
3. **Replace the nameless-mesh text proxy with material-driven detection.** Key `useAlphaAsRGB` /
   `prelit` off the material's authored font-texture + `pre_lit`/`use_environ` properties (which
   `RndMat` already carries) rather than `mesh->Name()[0]=='\0'` + name substrings. This removes the
   impostor-billboard collision (§1i), the `"icon"` exclusion, the `num*/_source/_comma/.lbl`
   broadening, and the `font`/`label` matName net — one data-driven rule replaces six string tests.
4. **Fold the highlight-bar + scrollbar-thumb placement fixes into the lane-3
   transform-propagation fix.** Both are `SetWorldXfm`-doesn't-reach-skinned-bones. Fixing the
   general skinned-UI world propagation deletes two name-scoped hacks (`RB3_NO_HUB_BAR_PLACEMENT_FIX`
   and the scrollbar block).
5. **Delete the ≥0.6 color floor (§1e).** It has no faithful basis and can only diverge from retail.
   If legibility is genuinely worse than retail after (1)-(3), that's a data problem to fix in the
   asset layer, not a per-channel clamp.

### B. Screenshot-diff regression harness

`scripts/analysis/visual_diff.py` exists and is already the render-change gate used elsewhere.
Propose a UI-parity gate on top of it:

- **Reference set:** `images/retail-screenshots/` — specifically `yt_qRagnZCIMzk_song_select_list.png`
  (Wii, "VIEWING n OF 587 SONGS" list), `..._song_select_album_art.png`,
  `..._song_select_diff_ratings.png`, `..._song_select_filter_panel.png`, and
  `yt_mhKNp9uAT48_menu_hub.png` (360 hub). All are 1280×720, matching the native canvas.
- **Capture path:** drive `rb3-native` headless via the HTTP debug API (`/api/screenshot` →
  PNG), navigating to each screen with `/api/input` nav verbs — the exact harness pattern in
  `scripts/native/song-select-capture.py` (the memory index calls this "the UI-visual-test
  template").
- **Metric:** because layout parity (positions/overlap) matters more than exact color on a synthetic
  lighting build, gate on **structural** differences: per-region SSIM + a text-bounding-box overlap
  check (detect the stale-slot overlap and the squished/tall-glyph regressions specifically), rather
  than a global pixel RMSE that the synthetic lighting would swamp. Seed regions from the reference
  layout (list rows, header band, right album/difficulty panel, footer action bar).
- **Guard against the known blind spot:** prior visual gates were "blind to patch-shard corruption"
  (memory) — a global drop/ratio metric PASSed on exploded frames. For UI, use per-slot text-region
  checks so a stale/overlapping row fails even when the whole-frame metric is fine.
- **Run it in the integration-worktree full-rebuild gate** (the method the decomp campaign found
  necessary to catch cross-inliner regressions) so a UI heuristic change can't silently regress a
  different screen — exactly the "one fix per screen" churn this review is trying to end.
