# ghidriff correlator calibration — Bank5 vs Bank8 name oracle (2026-06-09)

**What:** scores every ghidriff (VersionTrackingDiff, `--no-symbols`) correlator
against ground truth, so we know which match types to trust at which function
sizes before pointing the pipeline at a cross-compiler target (Xbox 360) where
ground truth is scarce.

**Oracle:** Bank 5 (`band_r_wii.elf`, 2009 DWARF) and Bank 8 (`bank8_target.elf`,
2010 target) both have full CodeWarrior linker maps; 41,680 mangled names are
common to both maps (all sections), of which **26,534 are code-section
(function) names** → **26,517 strict 1:1 oracle pairs** (name unique in each
map). A name-blind match is "correct" when both matched addresses resolve to the
**same mangled symbol**; the softer *base* metric also accepts signature-only
renames (same pre-`__` base identifier, distill_ghidriff.py's `base_match`).

**Generated by:** `tools/ghidra/calibrate_ghidriff.py` (pure JSON streaming —
no Ghidra). Re-run with:

```bash
build/SZBE69_B8/ghidra/ghidriff-venv/bin/python tools/ghidra/calibrate_ghidriff.py
```

## Coverage: full match list, not just modified pairs

`divergence_index.json` only covers pdiff's `functions.modified` (~10k changed
pairs). But the run also wrote
`json/band_r_wii.elf-bank8_target.elf.ghidriff.matches.json` (2.5 GB), whose
`address_matches` section is the **complete per-correlator match record** —
including the ~44k matched-but-unchanged pairs and the full
BulkBasicBlockMnemonicHash many-to-many explosion (11,154,136 pair records,
reconciling exactly with the log's per-correlator Counter). **Calibration below
therefore covers the entire match corpus**, except the Implied-ratio sweep,
which needs `m_ratio` and is thus modified-pairs-only (a near-total view anyway:
5,565 of 5,686 Implied pairs are in the modified set).

### Validation (join sanity)

The `<16B` ExactBytes bucket degrades to 63% as predicted by the known 8-byte
cross-class stub collisions, and the known example appears verbatim:
`SetBaseKerning__7RndFontFf` (b5) ↔ `SetFrameMicPitch__6SingerFf` (b8, 8B);
also e.g. `GetBandContribution__5StatsCFv` ↔ `GetSpeed__14StandardStreamCFv`.
SymbolsHash scores 100.0% in every bucket, as a name-based correlator must.

## Recall — which stage first proposed the correct pair

Of 26,517 strict oracle pairs: **17,454 (65.8%)** had the correct pair proposed
by ≥1 correlator; 2,522 were proposed only to *wrong* partners; 6,541 never
appear in any match (includes functions Ghidra never defined and dead-stripped
duplicates, so true recall on Ghidra-visible functions is higher).

BulkBasicBlockMnemonicHash's 5,138 are **proposal-only**: the correct pair

That 5,138 is *recall headroom* for a sane (uniqueness-filtered) bulk-mnemonic
correlator.

## Interpretation

1. **ExactInstructionsFunctionHasher is the workhorse**: 97.9% exact identity,
   ≥95% in every size bucket, 3,156 oracle pairs caught name-blind. Trust it
   outright.
2. **ExactBytesFunctionHasher is trustworthy only at ≥16B** (94-99%); below
   16B it collapses to 63% — every PPC getter/setter stub is byte-identical.
   Gate exact-byte matches on function size, not on the "exact" label.
3. **StructuralGraphExactHash is a trap despite its name**: 46.7% exact —
   CFG shape collides massively on compiler-regular code, even at 256B+
   (48.2%). Treat it as a weak hint, never an identity claim. Same for
   **SigCallingCalledHasher (1.4%)** and **Decomp Match (0/15 correct)**.
4. **StringsRefsHasher is the strongest non-instruction signal** (91.4% exact,
   93.6% base) — important for Xbox 360, where instruction/byte hashers can't
   fire cross-compiler but string refs survive.
5. **Raw Implied Match is 26% precise — never auto-trust it.** Two gates fix
   it: dedupe to 1:1 (84.3% exact on its own) and require `m_ratio >= 0.9`
   (together: **90.4% exact / 93.9% base**, keeping 459 of 5,565).
   Recommended future default: `--implied-min-ratio 0.9` *plus* 1:1 dedupe;
   0.95 if used for unattended name/type porting.
6. **BulkBasicBlockMnemonicHash should be disabled** for the 360 run: 11.1M
   many-to-many records (99.8% of the 2.5 GB matches.json, 168s runtime),
   ~0% precision, zero accepted matches. Its only value is latent recall
   (5,138 correct pairs buried in the noise) that ghidriff's assignment
   can't extract anyway.
7. Multi-match behavior generalizes: for every one-to-many source (Bulk,
   Implied), the **1:1 subset is dramatically more precise** than the rest
   (Implied 84.3% vs 26.5%; Bulk 42.3% vs 0.0%). Uniqueness is itself a
   high-value correlator feature.
8. Exact-name precision is a *lower bound* on true match quality (a "wrong"
   pair can be a genuine rename or a duplicated identical body — e.g. the
   86.9% ExactBytes 256B+ cell is partly identical-body twins), but the small
   exact→base gaps show most misses are real misidentifications.
