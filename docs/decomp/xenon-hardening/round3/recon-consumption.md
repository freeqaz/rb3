## A. WORKLIST FORMAT + LOCATION for #1

### A.1 How the active effort actually decides what to port (the consuming pipeline)

The active methodology is "class-A TU-pure port-then-pin", driven by
**`rb3-xenon/scripts/wf_classa_harvest.js`** (an `ultracode`/Workflow script;
latest is wave-3, commit `5b435c6`). Its three phases and what they consume:

1. **Scan** (`scripts/wf_classa_harvest.js:37-47`) — a string-anchored-core scan over
   `fingerprints.json` (string→VA index, rarity ≤ 3) finds an UNPINNED game TU whose
   methods form a contiguous TU-pure span in an unpinned gap of
   `config/45410914/splits.txt`. Excludes a hardcoded `DONE_OR_MIXED` list
   (`:14`). Emits candidate `{name, tu, wii_path, dst_path, core_va, gap_kb, core_fns}`.
2. **Validate** (`:49-58`) — per candidate, attributes each gap fn to a TU. It uses
   `unified_id_rb3wii.json` but EXPLICITLY discounts it as a **"NEAR-RANDOM oracle"**
   (`:52`), leaning on distinctive-string cross-match + bl call-topology. Verdict
   `OWN` only if `max_foreign_zero_run < 8`. **This stage is the weak link**: the
   prompt itself warns "the validate stage OVER-CLAIMS OWN as the pool thins".
3. **Port** (`:60-67`) — port rb3-Wii source → MSVC X360 in a worktree, pin `.text`,
   run `tools/gen_game_target_map.py --tu <TU>` (ADD-ONLY) to pair, re-`report.json`,
   honest A/B + ICF-fold guard.

The identity oracle in the loop today is `unified_id_rb3wii.json` (cross-arch BinDiff,
measured **near-random** for game code — see `docs/plans/bindiff-vs-rb3wii.md` and the
fuzzy reframe). **Our 232 band3 ghidriff identities are a strictly better per-fn oracle
(0.900 human-judged)** that pins specific Xenon addrs to specific Wii functions in
specific TUs — exactly the `OWN`-attribution signal the Validate stage is weakest on,
AND a TU-priority signal for the Scan stage (a TU with N high-confidence pinned
identities is a proven-real port target, not a string-anchor guess).

`fn_resolver.py` ALREADY consumes the full 978 as tier **T4b `ghidriff_wii_b8`**
(`tools/fn_resolver.py:574-628`, confidences 0.94/0.93/0.90 by match type) — but only
for *resolving a known fn_ address*. It does NOT surface a band3 **TU-ranked porting
queue**. That queue is the gap #1 fills.

### A.2 Why NOT target_symbol_map injection (constraint 3, re-confirmed)

`scripts/target_symbol_map.json` is consumed by `obj_target_symbol_renamer` (pre-compile
build step) to rename the dtk-split *target* obj's `fn_<addr>` → MSVC-mangled, so
objdiff pairs by name. For a not-yet-ported TU **there is no compiled MSVC symbol to
pair to** — `gen_game_target_map.py` only emits an entry when it finds the *defined*
MSVC symbol in our compiled `.obj` (`gen_game_target_map.py:316-365`,
`parse_coff_defined` requires `secnum > 0`). Worse, our `wii_symbol` is **CW/MWCC-mangled**
(e.g. `ShowClothes__9ClosetMgrFv`), NOT MSVC-mangled; injecting it would be a wrong key
that mis-pairs objdiff at our ~0.90 precision = actively harmful. Confirmed: the
production map keys are MSVC mangled (`?Method@Class@@...`), our names are CW. They are
NOT interchangeable.

`true_progress.py` / `fuzzy_progress.py` are pure read-only classifiers of the
`report.json` near-miss pool — they consume report.json, not an external feed — so the
worklist is NOT a progress-tooling injection either.

### A.3 RECOMMENDATION — the single best form + location

**Two coupled outputs, additive + reversible, NOT touching target_symbol_map:**

**(1) Machine-readable data feed — `rb3-xenon/band3_port_worklist.json`** (repo root,
gitignored like its sibling `ghidriff_identities.json`; regenerated by a tracked
generator script). One entry per net-new band3 identity (232), grouped consumption is
by TU. This is what the `wf_classa_harvest.js` Scan/Validate stages read as a
priority + attribution oracle.

Exact per-entry fields (superset of what both stages need):
```json
{
  "rb3_addr": "0x825508c8",            // Xenon target addr (lowercase 0x). Join key into report/splits.
  "wii_addr_bank8": "0x802ac920",      // Bank-8 Wii addr (NOT Bank 5) — for bin/analyze-function on the rb3 side
  "wii_symbol": "ShowClothes__9ClosetMgrFv",     // CW/MWCC-mangled (the identity oracle, ground truth)
  "wii_demangled": "ClosetMgr::ShowClothes(...)", // HUMAN-READABLE — see A.4 (NOT present in the ingested file; must be generated)
  "tu": "ClosetMgr.o",                 // groups the worklist; maps to ../rb3/src/.../ClosetMgr.cpp
  "match_type": "ExactInstructionsFunctionHasher", // primary match_types[0]
  "confidence_label": "high",          // high | bsim>=30 | bsim20-30 | bsim15-20  (the certainty stratum)
  "simconf": null,                     // BSim similarity*confidence, or null for exact/switch/implied
  "dc3_cannot_provide": true           // ALWAYS true for category==band3 (RB3 gameplay; DC3 has no Rock Band)
}
```

**(2) Human-facing TU-ranked markdown checklist — tracked at
`rb3-xenon/docs/plans/band3-port-worklist.md`** (sits beside the existing
`porting-backlog-ranked.md` / `porting-wave-1.md` / `game-code-pairing.md` plans that
porters already read). It is a TU-by-TU table RANKED by `(#high + #bsim≥30) desc, then
total identities desc`, each row: `TU | #ids | high | bsim≥30 | bsim20-30 | bsim15-20 |
top demangled methods | ../rb3 src path | DC3-cannot-provide`. The Scan stage's
`DONE_OR_MIXED` exclusion and the porter pick the next TU from THIS ranking instead of
a blind string-anchor guess; the Validate stage cross-checks its `OWN` verdict against
the per-fn identities in the json feed (a fn the json pins to this TU at `high`/`bsim≥30`
confidence is strong evidence FOR `OWN`, independent of the near-random rb3wii oracle).

**Why this form, not the alternatives:**
- A pure json feed alone wouldn't be *picked up* — the harvest workflow's TU choice is
  human/coordinator-driven from the `docs/plans/*` markdown; the ranked .md is what a
  porter reads. A pure .md wouldn't be *machine-ingestible* by the Validate stage.
- An additive `fn_resolver` feed is redundant: fn_resolver T4b already serves these 978
  for per-address resolution. The missing artifact is the **TU-priority + per-TU member
  roster**, which fn_resolver does not expose.
- Both outputs are additive and reversible: delete two files (one gitignored, one
  tracked doc); zero effect on the build, the map, objdiff, or report.json.

**Generator placement:** a tracked `rb3-xenon/tools/gen_band3_port_worklist.py` that
reads `ghidriff_identities.json` + `scripts/target_symbol_map.json` (net-new filter) +
the CW demangler, emits both files. Keep the data file gitignored + regenerable; commit
only the generator + the markdown. (Branch-check rb3-xenon before any commit per
constraint 2; it was on `main` at recon time.)

### A.4 Human-readable signature — the CW demangler IS the answer (verified)

CRITICAL measured finding: in the ingested file, **`wii_symbol_demangled` == `wii_symbol`
for ALL 232 band3 entries** (Ghidra's CW demangler no-op'd them). So the worklist MUST
demangle the CW name itself. rb3-xenon's `parse_wii_name`
(`tools/gen_game_target_map.py:184-227`) does NOT help — it expects *Ghidra-demangled*
input (`Class::Method(args)` with `::` and `()`), not CW-mangled.

**Use the round-2 CW demangler:
`rb3/docs/decomp/xenon-hardening/round2/forensics/demangle_cw.py`** — entrypoint
`demangle(sym) -> str`. Verified on 12 band3 net-new symbols (all clean):
```
ShowClothes__9ClosetMgrFv                  -> ClosetMgr::ShowClothes(...)
InOverrideFlow__13OvershellSlotCF...       -> OvershellSlot const::InOverrideFlow(...)
__ct__22TourHideShowFiltersMsgFb           -> TourHideShowFiltersMsg::TourHideShowFiltersMsg(...)  [ctor]
GlobalOptionsNeedsSave__10ProfileMgrFv     -> ProfileMgr::GlobalOptionsNeedsSave(...)
```
It renders args as `(...)` (doesn't expand param types) but gives `Class::Method`,
const-qualifier, and ctor/dtor correctly — sufficient for a human porting worklist.
For the full signature, the worklist can ALSO carry the raw CW `wii_symbol` (which a
porter reads via `bin/analyze-function <wii_symbol>` in the rb3 repo to see the real
Bank-8 body + arg shape). Recommendation: store BOTH (`wii_symbol` raw + `wii_demangled`
human form). Copy `demangle_cw.py` into rb3-xenon `tools/` (or import by path) so the
generator is self-contained.

### B.5 What the judges must watch for (the measured prior)

Round-2 human judging (band3, n=30) = **0.900 overall / 0.905 BSim**. The dominant and
ONLY failure mode across all 3 wrong pairs = **same-TU SIBLING ALIASING**: near-identical
